Reviving L2JFree · Part 8

Old bugs, new invariants

A 2009 game server carries the defect classes of its time: predictable secrets, comparisons that stop early, lost updates, integer overflow, and operations that finish halfway. For each class: the cause, the invariant that replaced it, and the check that keeps it out.

30 October 2026 · 7 min read

Reading old code for defects one by one is endless. Reading it for classes of defects is finite. Once you have seen one comparison that stops at the length of the shorter string, you know what to grep for, and you know what rule would have prevented it.

This article goes through the classes I found in L2JFree, with one or two examples each. It describes the class, the cause, and the fix. It does not describe how to exploit anything: every defect here is fixed in a released version, and the point is the pattern, not the attack.

Each fix in the project starts from an invariant, written at the top of its pull request: one sentence that must be true after the change. The invariants are quoted below, because they are the actual design.

1. Secrets from a game random generator

The cause. A game server is full of random numbers: drops, critical hits, spawn positions. They come from a fast generator with 48 bits of state, which is fine for a die roll. The same generator made the session keys that the login hands to the world, and the passwords that the optional telnet and remote administration generate. A generator with 48 bits of state can be reconstructed from a few of its outputs, and then its future outputs are known.

The invariant. A session key and a generated password come from a generator that cannot be predicted.

The fix. Both use SecureRandom.

The guard. A source rule in SourcePatternsTest fails the build if a SessionKey or a generated password is built from the game generator again. Fixing the instance is half the work; the rule is what keeps the next contributor from reintroducing it with the most natural line of code.

2. A comparison that stops early

The cause. The old password check compared the computed hash with the stored one up to the length of the stored value. An empty stored hash therefore matched every password. Passwords were also stored as unsalted SHA-1.

The invariant. A password matches only when the whole stored value matches, compared in constant time.

The fix. Passwords are stored as salted PBKDF2-HMAC-SHA256 with 600,000 iterations, and compared over their whole length in constant time. An account from the old line still holds its SHA-1 digest; it keeps working and is rewritten in the new form at its next successful login. Nobody has to reset a password, and no plain password is ever stored.

The guard. PasswordHasherTest: a new password is salted and verifies, the old form still verifies, a stored value that is empty, short, or broken accepts nothing, and only the old form or weaker iterations ask for a rehash.

3. Lost updates

The cause. Read a whole row, change one field in memory, write the whole row back. Anything another thread changed in between is silently undone. The login did exactly this with the account row: a ban set by a game master while a player was logging in could be undone by that login.

The password upgrade from the previous section has the same shape. A login reads the old hash, verifies it, and writes the new form. If the player changed their password in the meantime, a naive upgrade would overwrite the newer password with a rehash of the old one.

The invariant (#194). A login writes the last-active time, the address, and a password upgrade of the hash it verified. It does not replace a password that was stored after that hash was read.

The fix. A login writes only the columns it owns: the time and the address. The upgrade is a compare-and-set in SQL:

UPDATE account SET password_hash = ? WHERE name = ? AND password_hash = ?

Zero rows updated means a newer password won. The newer hash stays, and the login still succeeds.

The guard. LoginSchemaPostgresTest.passwordUpgradeDoesNotOverwriteANewerHash runs the statement against PostgreSQL 18: the first upgrade matches, a second one that still holds the old hash does not.

4. Integer overflow

The cause. The weight of an inventory was summed in an int: count times item weight, for every stack. A large enough stack makes the product exceed 2³¹ − 1, the sum wraps to a negative number, and every later check that compares the load with a limit sees an empty bag.

The invariant (#193). A weight check uses the full product of count and item weight. A product that does not fit in the accumulator is rejected.

The fix. The load is a long, and the addition refuses a product that does not fit even there. A stack of 400,000,000 arrows of weight 6 now weighs 2,400,000,000, not a negative number.

The guard. InventoryLoadTest covers that exact product, a product that does not fit in a signed long, and the saturation of the value sent to the client.

The same class appeared in money: an NPC sale that would push a player's adena past its cap is now rejected before anything is destroyed.

5. Operations that finish halfway

The cause. A trade moves items from one player to another, then the other way. A store takes the buyer's money, then moves the item. If the second half fails, the first half has already happened. In a game economy this is the difference between a failed trade and a duplicated or vanished item.

The invariant (#200). A confirmed player trade moves both sides or neither side. A line that cannot be transferred aborts the exchange and returns what already moved.

The fix. Each multi-step operation either orders its steps so that the risky one comes first, or undoes what it did when a later step fails:

  • a trade returns the lines it already moved;
  • an NPC purchase reserves the stock before it takes the money, and returns both if anything fails after the charge;
  • a buy store takes the money for one line before moving that item, and returns it if the move fails;
  • a player save writes everything in one database transaction (the subject of an earlier article).

The guard. Mixed, and honestly so. The save has a PostgreSQL test. The trade needs two live players and their inventories, and has no automated test yet: its fix was compiled and reviewed in CI, and its pull request describes the live check that would confirm it. That gap is written down, not hidden.

6. The right check on the wrong object

The cause. Remote administration generated a password when none was configured, logged it, and stored it on one instance of the service, then bound a different instance to the registry. The bound object kept an empty password. The password in the log did not work; an empty one did.

The invariant (#188). The object bound in the RMI registry is the one whose password was generated and logged. An empty password does not pass.

The fix. The generated password is stored on the instance that is bound, and every remote method rejects a null or empty password. The feature stays off unless an operator turns it on.

7. A key that is not bound to the client that showed it

The cause. The world accepted a session key and then authenticated whichever client was waiting for that account, not necessarily the one that presented the key.

The invariant (#26). The game client that presented the session key accepted by the login server is the client that becomes authenticated for that account.

The fix and the guard. A second claim for an account that already has a waiting or live session is refused. The answer from the login echoes the exact key that was checked, and the world authenticates the waiting client only if it matches. AuthLoginGuardTest locks the decision.

What the classes have in common

Almost none of these are clever. They are the ordinary failures of code written fast, for a small audience, with no one asking "what if this happens at the same time as that?". The fixes are ordinary too: a wider type, a WHERE clause, a reordered step, a real random generator.

What turns a fix into an improvement is the second half of each section: a rule, a test, or at least a written gap. A codebase does not get safer because someone fixed seven bugs. It gets safer when the eighth one of the same kind fails the build.

Where the series ends

This is the last note of the series. Eight notes followed one codebase from its silence in 2015 to release 3.2.1: the order of the revival, two servers in one process that still cannot see each other, a world of its own, a save in one transaction, a release rehearsed on every merge, a release that promotes what was tested, a start that was measured, not guessed, and, here, the defects of its time, each closed by a sentence and a check.

On 29 October 2026 the Java server left main. Its successor is written in Go, and the Java tests named above went with the code they guarded. The invariants did not have to. Each one is a sentence about behaviour, not about a language, and it is the first thing a new server has to answer. The next series begins with the first Go release.
