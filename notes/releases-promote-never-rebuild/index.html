Reviving L2JFree · Part 6

Releases promote, never rebuild

The release workflow of L2JFree has no build step. It finds the image that main already built and tested, verifies its signature, provenance, and SBOM, waits for a human, and gives that exact digest a version.

30 October 2026 · 6 min read

Most release pipelines rebuild. They check out a tag, compile, package, and publish. It feels natural, and it quietly breaks the promise that matters most: that what users run is what was tested. A rebuild pulls the base image again, resolves dependencies again, and runs on a different machine at a different time. The result is probably the same. "Probably" is a strange word to put in front of a release.

The decision

A release does not build anything. It promotes an image that already exists.

Every merge to main builds an image, puts it through the full rehearsal described in the previous article, and only then publishes it as edge and as sha-<commit>, signed and attested. A release picks one of those images by commit and gives that exact digest a version. Nothing is compiled, packaged, or pulled again.

What the release workflow does

release.yml is started by hand with a version and, optionally, a commit. It has two jobs.

verify checks everything that can be checked without a person:

  1. The commit is on main, and the tag v<version> does not exist yet.
  2. The pipeline of main passed for that commit. The workflow asks the GitHub API for a successful build.yml run on that exact SHA.
  3. The image sha-<commit> exists. Its digest is resolved once and used from here on, so a tag that moves cannot change what is released.
  4. The image is verified the way a user would verify it: the cosign signature against the identity of build.yml on main, the build provenance with gh attestation verify, and an SBOM that lists more than zero packages.
  5. Trivy scans the image under the vulnerability policy. A critical or high finding with a fix fails the release.
  6. The release notes are taken from the section of CHANGELOG.md with the same version. No section, no release.
  7. The Compose bundle is built with the image pinned by digest, so the archive a user downloads cannot start a different image than the one verified.

By default the workflow is a dry run and stops here. The dry run is how a release is rehearsed: it proves that everything is in place and shows the notes, and it publishes nothing.

publish runs only when the dry run flag is off, and only after a person approves it. It runs in a GitHub environment called stable-release with a required reviewer. The job sits and waits until the maintainer clicks "Approve and deploy".

Then it gives the verified digest the tags <version> and latest, reads the digest back and compares it, verifies the signature once more under the new tag, attests the Compose bundle, attaches the Sigstore bundle of that attestation to the release, and creates the git tag at the commit and the GitHub release.

The supply chain around it

Promotion only helps if the thing promoted was built honestly. The rest of the chain:

  • Actions pinned by commit. Every third-party action in every workflow is referenced by a full SHA, with the version in a comment. Dependabot proposes updates. A moved tag in someone else's repository cannot change what runs.
  • Keyless signing. cosign signs with a short-lived certificate tied to the workflow identity through GitHub's OIDC token. There is no long-lived key to leak. The certificate says which workflow, on which branch, signed the image, and verification checks exactly that.
  • Provenance and SBOM. Each image carries an SLSA build provenance attestation and an SPDX SBOM.
  • A signed archive. Since 3.1.1 the release attaches l2jfree-<version>-compose.tar.gz.sigstore.json. A user can verify the archive with nothing but the release page and gh:
gh attestation verify l2jfree-3.2.0-compose.tar.gz --repo l2go/alatyr \
  --bundle l2jfree-3.2.0-compose.tar.gz.sigstore.json \
  --signer-workflow l2go/alatyr/.github/workflows/release.yml

The --signer-workflow flag matters: without it, a provenance from any workflow of the repository would pass.

  • Scanning that means something. The first scan of the published image found twenty fixed high vulnerabilities. All of them were in captree, a Go program of the Arch Linux base that the server never runs. The image dropped it, and the content check fails if it comes back. The Java libraries had none.
  • Least privilege for tokens. Every workflow starts with read-only permissions. A job that writes packages or creates a release asks for that permission itself, in that job only.

What it cost

  • The image has to still exist. A daily job deletes sha-* image versions older than 30 days, unless they carry another tag. A released digest carries its version tag, so the job never touches it; an unreleased commit older than a month can no longer be released. That is deliberate: a release should be cut from recent, rehearsed work, and the registry should not grow without bound.
  • Only a person can withdraw a release. No job deletes a versioned image, but the maintainer can, and once did: the images and archives of every release before 3.2.0 were removed, because they carried the game world the project had inherited and has since left behind (part 3). Their release pages stay as history. A promise to keep artifacts forever is only as strong as the reasons to keep them.
  • A release is only as good as main. There is no release branch to patch in isolation. A fix lands on main, passes the rehearsal, and is then promoted. For a project with one maintainer that is a simplification, not a loss.
  • A human in the loop. The approval step means a release cannot happen at 3 a.m. by accident, and also cannot happen at 3 a.m. on purpose without someone awake. That is the intended trade.
  • The workflow identity is part of the contract. Users verify against build.yml@refs/heads/main and release.yml. Renaming either workflow changes what users must type. It is written into the security policy for that reason.

How it is verified

The release of 3.2.0 went through both jobs on 15 October 2026. The image of the release commit, sha-f61077f25d75, had passed the rehearsal and was published as digest sha256:5ea3aa84…10116db. A dry run verified it and built the bundle with that digest pinned in its Compose file. Then the release run verified everything again and waited about five minutes for the approval. The publish job gave the same digest the tags 3.2.0 and latest; one image now carries four names, 3.2.0, latest, sha-f61077f25d75, and edge, and one digest.

Afterwards, outside CI, the archive downloaded from the release page matched its checksum and was byte for byte the archive of the dry run, built in a different run. gh attestation verify confirmed the provenance of the image, signed by build.yml on main for commit f61077f, and the provenance of the archive, signed by release.yml.

None of this needs trust in the maintainer's machine, because the maintainer's machine never touched the artifact.
