Reviving L2JFree · Part 1

Reviving an abandoned MMO server: 2009 → 2026

An archived Lineage II server became one Java 25 process on PostgreSQL 18, shipped as a signed image. The revival changed one boundary at a time, kept a runnable server after every step, and made client sessions and recovery rehearsals part of the pipeline.

12 October 2026 · 8 min read

The last upstream commit landed on 15 July 2015. Its message was "README.md edited online with Bitbucket". Behind it lay nearly nine years of history: 8,044 commits under 24 author names, starting in November 2006. Together they made an open-source server for Lineage II, an online role-playing game, written for its Western Gracia Final client of 2009. The upstream repositories are archived on GitHub now; one of them describes itself as the project "as it was when it was abandoned".

I picked it up on 18 September 2026 and released 3.0.0 on 11 October. The work did not replace the server. It was a sequence of changes to its build, persistence, process boundary, and delivery, with a runnable server after each one. This series is about what happened between those dates and why: which decisions I made, what each one cost, and how each one is checked.

What I found

Most of the code still compiled. What stood in the way:

  • Two processes. A login server and a game server talked over their own socket protocol. A game server registered with a hex id file, a game_server table, and a register_gameserver tool.
  • MySQL everywhere. The datapack alone held 225 SQL files, with installers, update scripts, and a table optimizer. The login kept its accounts through Hibernate.
  • Collections that hid bugs. Javolution's FastList and FastMap let a loop remove from the collection it walked. On the JDK collections those loops throw, and some of them had been wrong for years.
  • Security of its time. The keys that the login handed to the world came from the fast game random generator, whose 48 bits of state can be recovered from a few outputs. The password check stopped at the length of the stored value, so an empty stored hash accepted any password.
  • An economy with holes. Item weight was summed in an int, so a big enough stack wrapped to a negative load. Trades and stores could move one side and fail the other.

These were the constraints of this fork: an old deployment model, database-specific code, and correctness defects that needed regression checks before they could be fixed for good.

The rules I worked under

One maintainer and a public repository. That set three rules before any code changed.

  1. GitHub Actions is the server's only build of record. The Java server is built, tested, and run there, never on a workstation, and a change is accepted on what the pipeline recorded. This removed "works on my machine" from the vocabulary and forced every recurring check to be automated from the first day.
  2. Every change explains itself. Each pull request states the issue, the invariant it restores, what changes for a running server, how it was verified, and what it leaves out. The pull requests became the design log.
  3. Test each claim where it can fail. Unit tests check local decisions. Integration tests on PostgreSQL 18 check the schema and persistence. Client sessions against the built image check what neither can: that the delivered system admits a player and keeps the data across a restart and a restore.

The order of the work

Replacing the server would have meant validating a new implementation as well as a new delivery model. I kept the inherited implementation as the checkpoint instead: each step left a server that started and could be checked. The work came in two phases: modernize the existing shape first, then make a deliberate cutover to Platform 3.0.

First, modernize in place. For two and a half weeks the server kept its shape: two processes on MySQL. A root build and CI on every push came first. Then a correctness program filed every defect as a broken invariant, one issue and one pull request each, and shipped as 1.4.0 on 25 September. The login moved to JDBC and both servers to Java 25 in 1.5 on 29 September. HikariCP, SLF4J, and a release with checksums, an attestation, and an SBOM followed in 2.0.0 on 30 September, and the test suite came back into CI in 2.5.0 on 5 October. The 2.x line was played on its real target, Windows with MySQL 8.4.

Then decide what 3.0 is. On 5 October the decisions for Platform 3.0 were recorded and the 2.x line was retired. The in-place line had done its job: the code was on a modern JDK, under tests, and released by a pipeline.

Keeping the modernized 2.x line was the other option. It would have kept MySQL and the separate login and world deployments. Platform 3.0 changed the database and the delivery together instead, and accepted a fresh world database and a single process. That was a choice of cutover, not a claim that the old shape could not be repaired.

A walking skeleton. A Linux image on a pinned base with a pinned JRE, a Compose stack that published ports 2106 and 7777, and a probe that sent the first packet of the login protocol. It did almost nothing, but it did it the same way every time.

The data, module by module. The login moved to PostgreSQL first: one schema, one Flyway migration, one role. The world followed with ten migrations, a catalog schema loaded from 57 CSV files with a SHA-256 revision, and a lock that keeps a second server off the same database.

One process. For one world on one host, the socket between login and world served no deployment the project needed. A small contract module with two interfaces replaced it, and architecture rules keep each module from importing the other's implementation.

The release. A workflow that promotes the image the pipeline already tested, after a human approves, with a signature on everything it publishes. Version 3.0.0 shipped six days after the decisions were recorded.

What it cost

Every one of these decisions had a price, and the series names it each time. The biggest ones:

  • No supported migration of 2.x world data. Platform 3.0 starts with a fresh world database. Old SHA-1 password hashes are still accepted and upgraded after a successful login; that is compatibility of the hash format, not a migration of the old database.
  • A smaller feature set. Factions, the community-board item auction, and the archive of deleted mail were removed rather than carried into the new schema, so the cutover changed what operators and players could use, not only the database engine.
  • One process shares one fate. Login and world now share a JVM's lifetime and memory. A crash takes both down; the article on boundaries explains why that trade was worth it.
  • One image platform in 3.1.1. The release covered linux/amd64 only; linux/arm64 arrived in 3.2.1.

What came out

Version 3.0.0 shipped on 11 October 2026. A day later, 3.1.0 closed a set of economy and login defects found by reading the code against its own invariants. 3.1.1 changed no game behavior; it made the release easier to verify. Each release is a signed image and a Compose bundle with a signature of its own.

The result is a changed delivery and persistence model, not proof that every inherited defect is gone. The pipeline checks module dependencies, the SQL of the world classes, client sessions, and recovery rehearsals. The costs are on record too: a fresh world database, removed features, and one shared process lifetime.

The rest of the series takes one decision at a time:

  1. One process, hard boundaries: two modules in one JVM, with dependencies checked at build time and separate database roles.
  2. An island of our own: how the server left an inherited world for one it wrote.
  3. One save, one transaction: how one save became one transaction, and what a rollback has to put back.
  4. Every merge is a release rehearsal: what the pipeline does to an image before it may be published.
  5. Releases promote, never rebuild: why the release workflow has no build step.
  6. Starting a Java 25 server: G1 against ZGC, with and without the AOT cache, measured in CI.
  7. Old bugs, new invariants: the classes of defects a 2009 server carries, and the checks that keep them out.
