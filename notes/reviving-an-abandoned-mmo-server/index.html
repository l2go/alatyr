Reviving L2JFree · Part 1

Reviving an abandoned MMO server: 2009 → 2026

An open-source Lineage II server went silent in 2015. Twenty-four days of work turned it into one Java 25 process on PostgreSQL 18, shipped as a signed image that CI plays on every merge.

12 October 2026 · 7 min read

The last commit before mine landed on 15 July 2015. Its message was "README.md edited online with Bitbucket". Behind it lay nearly nine years of history: 8,044 commits by 24 people, starting in November 2006. They built an open-source server for Lineage II, an MMORPG whose Gracia Final client shipped in 2009. The upstream repositories are archived on GitHub now; one of them describes itself as the project "as it was when it was abandoned".

I picked it up on 18 September 2026 to see how far a 2009 codebase can be carried by today's engineering discipline. Version 3.0.0 shipped on 11 October, twenty-four days later. This series is about what happened between those dates and why: which decisions I made, what each one cost, and how each one is checked.

What I found

The code still compiled, mostly. It also carried every habit of a 2009 game server:

  • Two processes. A login server and a game server talked over their own socket protocol. A game server registered with a hex id file, a game_server table, and a register_gameserver tool.
  • MySQL everywhere. The datapack alone held 225 SQL files, with installers, update scripts, and a table optimizer. The login kept its accounts through Hibernate.
  • Collections that hid bugs. Javolution's FastList and FastMap let a loop remove from the collection it walked. On the JDK collections those loops throw, and some of them had been wrong for years.
  • Security of its time. The keys that the login handed to the world came from the fast game random generator, whose 48 bits of state can be recovered from a few outputs. The password check stopped at the length of the stored value, so an empty stored hash accepted any password.
  • An economy with holes. Item weight was summed in an int, so a big enough stack wrapped to a negative load. Trades and stores could move one side and fail the other.

None of this is unusual. It is what a codebase looks like when nobody has been paid to say no to it for a decade.

The rules I worked under

One maintainer and a public repository. That set three rules before any code changed.

  1. GitHub Actions is the only build of record. Nothing is built, tested, or run on a workstation. If CI did not see it, it did not happen. This removed "works on my machine" from the vocabulary, and it forced every check to be automated from the first day.
  2. Every change explains itself. Each pull request states the issue, the invariant it restores, what changes for a running server, how it was verified, and what it leaves out. The pull requests became the design log.
  3. Prove it on the real thing. A test that runs against an in-memory fake proves less than one that runs against PostgreSQL 18 in a container. A server that starts proves less than one that a client logs into.

The order of the work

Big rewrites fail because they change everything at once and prove nothing until the end. I went the other way: each step left a server that started and could be checked. The work came in two phases.

First, modernize in place. For two and a half weeks the server kept its shape: two processes on MySQL. A root build and CI on every push came first. Then a correctness program filed every defect as a broken invariant, one issue and one pull request each, and shipped as 1.4.0 on 25 September. The login moved to JDBC and both servers to Java 25 in 1.5 on 29 September. HikariCP, SLF4J, and a release with checksums, an attestation, and an SBOM followed in 2.0.0 on 30 September, and the test suite came back into CI in 2.5.0 on 5 October. The 2.x line was played on its real target, Windows with MySQL 8.4.

Then decide what 3.0 is. On 5 October the decisions for Platform 3.0 were recorded and the 2.x line was retired. The in-place line had done its job: the code was on a modern JDK, under tests, and released by a pipeline. What was left could not be fixed in place.

A walking skeleton. A Linux image on a pinned base with a pinned JRE, a Compose stack that published ports 2106 and 7777, and a probe that sent the first packet of the login protocol. It did almost nothing, but it did it the same way every time.

The data, module by module. The login moved to PostgreSQL first: one schema, one Flyway migration, one role. The world followed with ten migrations, a catalog schema loaded from 57 CSV files with a SHA-256 revision, and a lock that keeps a second server off the same database.

One process. With both modules on the same database engine, the socket protocol between them had no reason to exist. A small contract module with two interfaces replaced it, and architecture rules made sure the modules could not reach around it.

The release. A workflow that promotes the image the pipeline already tested, after a human approves, with a signature on everything it publishes. Version 3.0.0 shipped six days after the decisions were recorded.

What it cost

Every one of these decisions had a price, and the series names it each time. The biggest ones:

  • A 2.x database cannot be migrated. The schema changed too much to carry the old data across honestly. A server starts fresh. The accounts are the exception: an old SHA-1 password still works and is upgraded at the next login.
  • Features without a home in the schema were removed. Factions, the community-board item auction, and the archive of deleted mail had no data model worth keeping.
  • One process shares one fate. Login and world now share a JVM's lifetime and memory. A crash takes both down; the article on boundaries explains why that trade was worth it.
  • linux/amd64 only. One image, one platform, until there is a reason for more.

What came out

Version 3.0.0 shipped on 11 October 2026. A day later, 3.1.0 closed a set of economy and login defects found by reading the code against its own invariants. 3.1.1 changed no game behavior; it made the release easier to verify. Each release is a signed image and a Compose bundle with a signature of its own.

Twenty-four people built it over nearly nine years. Twenty-four days rebuilt it. Twenty-four clients play it on every merge.

The rest of the series takes one decision at a time:

  1. One process, hard boundaries: two modules in one JVM that still cannot see each other.
  2. An island of our own: how the server left an inherited world for one it wrote.
  3. One save, one transaction: how a player and their items reach the database together or not at all.
  4. Every merge is a release rehearsal: what the pipeline does to an image before it may be published.
  5. Releases promote, never rebuild: why the release workflow has no build step.
  6. Starting a Java 25 server: G1 against ZGC, with and without the AOT cache, measured in CI.
  7. Old bugs, new invariants: the classes of defects a 2009 server carries, and the checks that keep them out.
