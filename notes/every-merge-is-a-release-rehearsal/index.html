Reviving L2JFree · Part 5

Every merge is a release rehearsal

Before an image may be published, the pipeline starts it, plays 24 client sessions, changes a setting, restarts it, stops it, restores a backup into a clean stack, and upgrades from the image already published. In 3.2 the same image also started on an empty world and sent 24 players to hunt.

30 October 2026 · 8 min read

Unit tests answer the question "does this function do what I think?". An operator asks a different one: "if I take this image and run it the way the guide says, will my players still have their characters tomorrow?". For a long time those two questions were answered by different people at different times. On L2JFree the pipeline answers both on every merge, before an image is allowed to exist in the registry.

The idea

Treat each merge to main as a full rehearsal of a release and of the operator's first week. If any step fails, nothing is published. The steps are not synthetic: each one runs the same commands that the deploy guide tells a person to run.

Everything below happens in the image job of build.yml, on a fresh GitHub runner, against the image that was just built from the verified distribution. In 3.2 two more rehearsals ran beside it; they come after the list.

The rehearsal

1. Build and inspect. The image is built, and its content is checked: the files that must be there, and the ones that must not. The world inside the image must equal the one in the repository, file by file. Trivy scans it. A finding with a fix does not block a merge; it blocks a release and fails the daily scan of the published image. A merge should not wait on a CVE in a base package that the server never runs.

2. Start it as an operator would. docker compose up -d --wait with the same Compose file the guide uses. A probe sends the first packet of the login protocol to port 2106 and connects to 7777.

3. Play a whole session. A headless client written for this purpose, a small Java program with no dependencies beyond the JDK, logs in, picks the server, creates a character, enters the world, and logs out. It uses an account that a later step must find again.

4. Play 24 sessions at once. Twenty-four clients, six at a time, each with an account of its own. Accounts, characters, and object ids are made concurrently, which is where id allocation and login races show up. This is a correctness scenario, not a capacity claim: it proves that concurrent sessions do not corrupt each other, not how many players a server holds.

5. Check the boundaries. Each database role runs statements against every schema and must reach only its own. Neither may be a superuser or create a schema.

6. Read the log. Each start is read on its own window of the log. It must name its world exactly once, as World id=buyan-okolitsa version=3.2.0, hold no ERROR line and no uncaught exception, and report no script that failed to load. A script that fails to load is not a startup error, so the server starts without it and nobody notices; the pipeline notices. Both ports must run on epoll.

That last check has a story. From its first build, the image ran on Java NIO without anyone knowing: /tmp in the container is a tmpfs without the right to execute, so Netty could not load its native library and fell back silently. Now Netty unpacks its native code into a directory that may execute, a transport that is not available stops the start, and the pipeline fails if a port is not on epoll.

7. Change a setting the way the guide does. The deploy guide changes the experience rate with one printf | docker compose exec -T server tee command. The pipeline runs that command, adding a key that no default file knows, then restarts the server and looks for the warning the server writes about that key. If the warning is there, the command wrote to the place the server reads. A documentation example that silently stopped working is a bug, and now it is a failing build.

8. Restart and find the character. After the restart, the account from step 3 logs in and must find exactly one character. Then it creates a second one.

9. Check the flight recorder and capture an incident. Java Flight Recorder runs from the start into the log volume; its chunks must exist. Then the incident script collects the logs, the slowest statements, the database sessions, and a thread dump from the running stack, and the server must still be serving afterwards.

10. Stop it and watch how it stops. The server must stop when asked, within the time Docker gives it, after saving the world, and without being killed. A save that never ends shows as exit code 137. The Compose file gives the server 60 seconds instead of Docker's default 10, because the save goes through the players one after the other.

11. Rehearse the backup and the restore. With the command from the guide: dump the login and world schemas, check that the dump holds accounts and players and does not hold the catalog, destroy the stack with its volumes, start a clean one, confirm the account is gone, restore, and start again. The account from step 3 must log in and find two characters. The role check runs again on the restored database.

12. Rehearse the upgrade. Start a stack on the image that is published now, edge, and make an account with a character. Replace the image with the one from this commit, on the same volumes. The new image runs its migrations over the old data, and the character must still be there. When 3.2 replaced the whole game world, this step showed exactly what an operator would see: the character survived, and seven of its items, whose templates the new world lacks, were skipped with a warning while their rows stayed in the database.

13. Only now, publish. On main, and only after every step above, the image is pushed, signed with cosign, given a build provenance attestation and an SBOM, and then verified with the same commands the security policy gives to users. A signature that does not verify fails the pipeline of main.

Two more rehearsals

Version 3.2 gave the image a world of its own, and two jobs rehearsed what the image job cannot. Both were later retired; part 3 records that.

An empty world. In 3.2.0 the empty-world job built the image from the same distribution and started it on a world directory that held nothing but a name and a version. The server had to reach readiness, open both ports, name the world as World id=empty version=0, and log no error. It told the operator, one line per part, what the world lacked. A server that only starts when everything is present has assumptions nobody wrote down; this job wrote them down.

A hunt. In 3.2.0 the seed-world job started the image on its own world and sent one player, then 24 at once, through the start of the game: leave the village, fight, pick up the coins, buy a potion and drink it, reach level 2, learn a skill, log out, and log in again to find everything as it was. Here even a warning in the server log failed the run. On the commit that became 3.2.0, all 24 finished in 120 seconds.

And before any of this, the world job checks the tree: the world the project inherited must not come back, and the world it ships must equal a fresh render of its sources.

What it cost

  • Time. The rehearsal takes minutes on every merge. For a project with one maintainer that is cheap: the alternative is a person doing it by hand, or nobody doing it.
  • A client to maintain. The headless client speaks the real protocol, so a protocol change means a client change. That is the point, but it is work.
  • Flakiness to fight. A test that starts containers and opens sockets can fail for reasons that have nothing to do with the code. All 24 clients come from the address of the Docker gateway, and one address may open only so many connections in a short time, so the pipeline raises the accept limits the way an operator behind such an address would. Every such fix is written next to the step, with the reason. The hunt brought its own: when 24 clients share one meadow, the client becomes a small distributed system, and its first bugs were its own. Part 3 tells that story.

Why it is worth it

Each step guards against a defect that really happened in this codebase. The silent NIO fallback is behind the transport check. The save of the raid bosses on shutdown never ended, which is why the stop is watched for a kill. A Python class stored in a global ran without its constructor, so some AI scripts never loaded and the server started anyway; that is why the log is read for every script. None of these would have shown up in a unit test.

More importantly, it changes what a green build means. Green does not mean "the code compiles and the tests pass". It means "this image started, served players, survived a restart, a restore, and an upgrade, and stopped cleanly". In 3.2 it also meant the image started on nothing and explained itself, and that 24 players hunted in its world. That is the sentence an operator actually needs to hear.

Update, 30 October 2026. The steps above are the rehearsal of the Java server, as it ran through release 3.2.1. The empty-world start and the hunt were retired on 23 October. On 29 October the Java server left main for a server written in Go, and the rehearsal changed with it. After every merge the image is now built natively for amd64 and for arm64, and each is started with PostgreSQL. An authenticated participant enters the world and moves. The server is stopped live and must have saved the move; it starts again, and the participant finds the saved position. A backup of the world schema is restored into an empty one, and the participant enters once more. Only then is the image published. The 24 sessions and the upgrade step went with the Java client and the Java data: the Go server starts from a fresh database and does not import an older one.
