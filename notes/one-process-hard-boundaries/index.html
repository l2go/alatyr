Reviving L2JFree · Part 2

One process, hard boundaries

Login and world used to be two servers joined by a socket protocol. Now they share one JVM, kept apart by a two-interface contract, eight dependency rules checked at build time, and a database role per module. The price is one shared process.

12 October 2026 · 6 min read

A Lineage II client connects twice: first to the login, then to the world. The login checks a password and hands the client a key; the world checks that key, lets the client in, and runs the game. L2JFree ran the two as separate processes that talked over a protocol of their own. The client needs two endpoints, not two programs.

The problem

Separate processes let login and world run on different machines. Platform 3.0 targets one world on one host, so that freedom was not a requirement, and the socket that bought it had a price:

  • Registration. A world announced itself to the login with a hex id file and a row in a game_server table, created by a register_gameserver tool. Get any of the three wrong and the world never appeared in the server list.
  • A protocol to keep in step. Every change to how a session key travelled meant a change on both sides, deployed together. One of the first fixes, binding a world login to the exact key the login had checked (#26), had to change both servers and the messages between them.
  • Two things to deploy, start, and watch. Two distributions, two launchers, two logs.

The decision

Run login and world in one JVM, and replace the protocol with a Java contract.

The alternative was to keep two processes behind a standard RPC. That would keep independent restarts and resource isolation, and let the two halves be placed or scaled apart. It would still need an endpoint, a remote failure model, and a message contract versioned across two deployments, though not the old hex-id registration. For one world on one host I chose the smaller operational surface: a Java contract removes the internal network hop, and pays with a shared process lifetime and shared resources, described below.

The contract is its own module, and it is small on purpose. It has two interfaces and a handful of value types.

LoginPort is what the world asks of the login:

public interface LoginPort
{
	AdmissionResult admit(String account, SessionKey key);
	void leave(String account);
	void changeAccessLevel(String account, int level);
}

WorldPort is what the login asks of the world:

public interface WorldPort
{
	WorldStatus status();
	String addressFor(String clientIp);
	void kick(String account);
	void expect(String clientIp);
}

That is the whole conversation between the two halves of the server. admit is atomic: when it admits an account, the account counts as in the world and its login session closes, so a second admission of the same account is refused. The packet exchange became an in-process call with a typed result. That removes transport failures from the exchange, not failures in the login or the world.

A platform module is the composition root: it starts both modules, wires each to the other's port, and assembles the one distribution. A dependency rule reserves knowledge of both implementations for it.

Keeping the modules apart

Merging two processes into one is easy. Keeping them from growing into each other is the actual work. In one JVM, nothing stops a class in the world from importing a class in the login, except a rule that fails the build.

The rules live in ArchitectureTest, written with ArchUnit. Each one carries its reason, so a failure explains itself:

RuleBecause
The login module does not depend on the world moduleThe two modules know only the contract, so either can be replaced or tested alone
The world module does not depend on the login moduleSame
The contract depends only on the JDK and itselfIt is the one thing both modules share, so it must pull in nothing of either
The login module does not use the world's Config or L2DatabaseFactoryEach module owns its configuration and its database role
Only the platform package depends on both modulesThe platform wires the two modules, and nothing else may
No cycles between login, world, and contractA cycle would make the modules depend on each other
The modules and the contract do not depend on the platformThat would be a cycle through the launcher
The network core knows no moduleIt is a reusable transport; the modules use it, never the other way round

One detail matters more than it looks: a rule that selects no class must fail rather than pass unnoticed. ArchUnit 1.5.1 fails such a rule by default, and this test does not opt out, so a typo in a package name turns into a red build instead of a green no-op.

The boundary continues into the database

A boundary that stops at the class path is half a boundary. If both modules connect as the same database user, the world can read the login's password hashes with one careless query, and no architecture test will notice.

So each module has its own PostgreSQL role. The login connects as l2jfree_login and owns the login schema. The world connects as l2jfree_world and owns world, catalog, and report. The pipeline checks this on the running image, not in a unit test: check-roles.sh runs as each role in a started stack. It checks representative allowed reads in login, world, and catalog; refused reads across the login–world boundary; that neither role may create a schema or an extension; and that neither is a superuser. It runs again after a backup is restored. It does not enumerate every grant, and it does not test the report schema.

These are boundaries of dependencies and database permissions, not a security sandbox: code in one JVM shares the process's memory and environment.

What it cost

  • Shared fate and resources. If the JVM dies, login and world stop together. They share heap, threads, and CPU, so a resource problem in the world can reach the login. I accepted that coupling for one world on one host: a login without a world is of no use to a player, and the world was always the part that needed watching.
  • No independent placement or scaling. The login cannot move to its own host without a remote adapter in front of the contract. The chosen deployment does not need that.
  • One deployment and restart boundary. Login and world ship and restart together. The image cannot hold mismatched versions of the two, and the halves can no longer be rolled out or restarted separately.
  • One status interface. The login's telnet status, with its four commands, was removed; the world's telnet status remains.

How it is verified

  • ArchitectureTest runs in every build. A dependency across the boundary fails the pull request with the rule's name and its reason.
  • check-roles.sh runs on every merge against the started image, and again after the restore rehearsal.
  • The removed pieces cannot come back unnoticed: RemovedLibrariesTest refuses MySQL, Liquibase, Javolution, Trove, and the old MMOCore network layer that Netty replaced.

The result is a modular monolith in the plain sense of the words: one thing to deploy, two things to reason about, and a build that keeps them two. It is not process isolation. A second world sharing one login, or a need to restart the halves independently, would be the reason to revisit the choice.

Update, 16 October 2026. In 3.2 the same idea, a boundary that a check keeps in place, separated the engine from its game world: the world became a directory the engine is pointed at. See part 3, An island of our own.
