Reviving L2JFree · Part 4

One save, one transaction

A character save and its item writes used separate database connections. A failure could leave them out of sync. One transaction now groups the save's writes, and rollback restores the item flags needed to retry. Writes outside a save keep their background queue.

23 October 2026 · 7 min read

In an online game, a lost or duplicated item changes what a player owns. L2JFree could save a character and its items independently, leaving them out of sync after a failure. The fix needed to make one save atomic without turning a persistence repair into a server-wide refactor.

The problem

In Lineage II, an online role-playing game, one player-controlled character spans several database rows. Depending on the save call and configuration, a save can include its character record, a companion pet if present, temporary status effects, and its inventory, the items it carries. In the inherited Java server, those writes did not share a transaction.

The character, pet, and effects were written on the thread running store(), the character-save method. Items went through an SQL queue: one background writer for the whole process that grouped writes on a separate database connection. It kept frequent item writes off the caller's path, which was worth preserving outside a save. But a save had two independent write paths, and store() could return before the queued item writes ran.

The consequences were the quiet kind:

  • A failure could leave the character and its items reflecting different save attempts.
  • After rollback, a later save could skip the item writes because the in-memory flags already said those items were stored.

Each item tracks two things: whether its database row exists, and whether that row matches the current in-memory values. A write updates that bookkeeping before the transaction commits. If the transaction rolls back, PostgreSQL discards the writes, but Java does not automatically restore the flags.

The decision

Put the writes selected for one player save in one database transaction. They commit together or roll back together. On rollback, restore the item flags to their pre-write values; keep the changed item values in memory so the next save can write them.

Passing a connection into every call is the better shape for new code, because the boundary sits in the signature and the compiler catches a missing one. Connection acquisition was spread across the persistence layer: 106 classes outside the factory acquired connections directly in the main sources of 3.1.1. That is the size of the layer, not the required change set for this save. Converting the whole layer to explicit connections would also require changing the inherited finally blocks that close connections or flip auto-commit. I chose to establish this save boundary through the existing factory instead.

Enlisting the SQL queue was the other local option. The queue is one deque for every player, drained on another thread, each statement committing alone; pulled into this save, it would commit or roll back other players' writes with it.

An outbox would commit the character row and apply the items later, which is the split this change removes. XA would add distributed-transaction coordination where one PostgreSQL transaction is enough.

So the save boundary goes through the existing connection factory, and during a save the item writes bypass the queue and join the character's transaction. Outside a save, they keep the queue.

A transaction that follows the thread

WorldTransaction runs a piece of work in one database transaction. While it runs, every connection that L2DatabaseFactory.getConnection() hands out on the same thread is the connection of the transaction. The old code keeps calling the factory exactly as before; it just gets the same connection each time.

boolean committed = WorldTransaction.run("store the player", () -> {
	// everything here that asks the factory for a connection
	// gets the one connection of this transaction
});

Existing methods still close their connections in finally blocks, and some change auto-commit, the mode in which each SQL statement commits on its own. They cannot be allowed to end the surrounding transaction. The factory therefore returns a wrapper around the real connection. It ignores close, setAutoCommit, and the no-argument commit() and rollback(); WorldTransaction owns the final commit or rollback. Nothing in this tree takes a savepoint. A nested call joins the outer transaction rather than starting an independently committed one.

The work rolls back when it throws. The inherited item writes, though, do not throw: they catch a failure and log it. On PostgreSQL a failed statement aborts the transaction, and WorldTransaction checks with SELECT 1 before committing, so a swallowed SQL error still rolls the whole save back. A failure that is not an SQL error, caught inside an item write, does not abort the transaction, and the rest of the save can commit.

Making a failed save retryable

PostgreSQL rolls back database writes; it cannot roll back fields in a Java object. The item flags therefore need their own undo step.

WorldTransaction.onRollback(Runnable) registers code to run if the transaction rolls back. Before writing, an item records its existing flags. Rollback restores those flags, not the item's gameplay values. The changed item still needs saving, and the next save no longer skips it.

The change in #162 is small, and narrower than "every save". L2Player.store(true, true), the call a disconnect makes, writes the player's inventory and the pet's inventory on the same connection as the character, the pet, and the effects; a disconnect tries that save up to three times. The periodic auto-save calls store() without arguments, and with the shipped UpdateItemsOnCharStore = False it does not write the player's inventory. The pet's inventory is written on every save. Item writes outside a save still go through the queue.

What it cost

  • Row locks held until the commit. The rows belong to one player's save, not the whole world, but another writer of those rows waits, and the queue is such a writer. This change does not establish a save-latency or throughput budget.
  • Two item-write paths. Outside a save, the queue still takes the write: one shared deque, another thread, its own connection. A queued write and a save of the same item both take that item's monitor, and the queue reads the flags again before it chooses insert, update, or delete. That ordering is part of correctness and has to stay true as the code changes.
  • An implicit transaction dependency. Callers keep the factory API, so the active transaction is invisible in their parameters, and work handed to another thread leaves it behind. One save does not change thread. For the same reason, the shared queue must not be flushed while the save transaction is active: it asks the factory for a connection, so it would join this transaction and carry every other player's pending writes with it.
  • A pet edge that is not closed. A pet row references its control item, the inventory item that identifies the pet. Before #162 the save flushed the queue first, so that item was committed before the pet. That flush is gone, and the periodic save does not write the player's inventory, so on that path the control item can still be waiting in the queue when the pet row is written.

How it is verified

Two tests guard the mechanism, against PostgreSQL 18, not a mock. L2DatabaseFactoryTransactionTest guards the one connection per thread, the wrapper that cannot end the transaction, and the rollback after a swallowed SQL error. PlayerItemSavePostgresTest guards the character and the items:

  1. Save an existing item row with quantity 4. In memory, change its quantity to 9 and create another item with quantity 3.
  2. In one transaction, write both items and a new character title, a display label, then throw an exception to force rollback.
  3. Reopen the pooled database connections and read through fresh ones. The title is unchanged, the new item is absent, and the existing item still has quantity 4. In memory, the new item knows it has no row; the existing item knows its row exists but does not match memory, and its quantity is still 9.
  4. Save again without the exception. Read through fresh connections again: the saved title and item quantities 3 and 9 are all present.

Step 3 checks that rollback leaves the previous database state visible through new connections. Step 4 checks that the same in-memory items can still be saved afterwards. Refreshing the connections is not a server restart; this test isolates rollback and retry, not crash recovery.

The same transaction later carried two more fixes, and they are not the rollback hook. Replacing a subclass, an alternate class a character can switch to, deletes the old row and inserts the new one in one transaction (#203). The character's map drops that subclass only after the transaction commits, so a rolled-back delete leaves it in the database and in memory (#175). Neither fix is covered by the tests above.

The database must commit the save as a unit; the objects must still know what needs saving if it rolls back. That is the boundary: one player save, not one SQL statement.

Update, 23 October 2026. The project's Go world module names the same distinction. Commit records an in-memory gameplay outcome, not a database commit. For skill learning, Durability reports the result of the subsequent storage write. If that write fails, the learned state remains in memory and its outcome is not rewritten as a rollback. These are separate promises; the module does not provide transactional persistent storage.
