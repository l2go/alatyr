Reviving L2JFree · Part 4

One save, one transaction

A player save wrote the character on one connection and the items through a background queue, so a failure in between could split them. A thread-scoped transaction and a rollback hook made the save atomic without rewriting 2009 persistence code.

23 October 2026 · 5 min read

In an MMO, the worst bug is not a crash. A crash loses a few minutes for everyone, and players forgive it. The worst bug is one that loses or creates an item for one player, because then the economy stops being fair and nobody can prove what happened.

The problem

A Lineage II player is not one row. A save writes the character, the pet if there is one, the active effects, and the inventory. In the inherited code those writes did not share a fate.

The character and its satellites went to the database on the saving thread. Item writes went through an SQL queue: a background writer that batched statements on a connection of its own. The queue existed for a good reason, since items change constantly and writing each change at once would hammer the database. But it meant that a save was really two saves, and only one of them was finished when store() returned.

The consequences were the quiet kind:

  • A save that failed halfway left the character as it was and the items as they were going to be, or the reverse.
  • A new pet failed on its foreign key, because the control item that owned it was still waiting in the queue.
  • A save that rolled back on disconnect was never repeated: the in-memory flags said the items were already stored.

The last point is the subtle one. Every item carries flags that remember whether it exists in the database and whether its row matches memory. A write sets them. If the transaction that held the write rolls back, the database forgets the write, but the flags do not.

The decision

Make a save one transaction: the character, the pet, the effects, and the items reach the database together or not at all. When it rolls back, memory goes back to what the database holds, so the next save writes everything again.

The obvious way to do this is to rewrite every persistence call to take a connection parameter. In a codebase where more than a hundred classes ask L2DatabaseFactory for a connection directly (106 in the main source of 3.1.1), that is a rewrite of the server. I took a narrower path.

A transaction that follows the thread

WorldTransaction runs a piece of work in one database transaction. While it runs, every connection that L2DatabaseFactory.getConnection() hands out on the same thread is the connection of the transaction. The old code keeps calling the factory exactly as before; it just gets the same connection each time.

boolean committed = WorldTransaction.run("store the player", () -> {
	// everything here that asks the factory for a connection
	// gets the one connection of this transaction
});

Old code also does what old code does: it closes its connection in a finally block, and sometimes it toggles auto-commit. Inside a transaction, either would end it early. So the connection handed out is a proxy that turns close, setAutoCommit, commit, and rollback into no-ops. The work cannot end the transaction; WorldTransaction commits when the work returns and rolls back when it throws. A call made inside another transaction joins the outer one, so nesting does not commit halfway.

Putting memory back

The database half of a rollback is free. The memory half is not, and it is where most "transactional" game code is quietly wrong.

WorldTransaction.onRollback(Runnable) registers an undo step. An item that writes its row inside a transaction registers the step that restores its flags. If the transaction rolls back, the database discards the row and the undo step tells the item it is not stored after all. The next save sees an item that needs writing, and writes it.

With that in place, the change itself (#162) was small: L2Player.store writes the inventory, and the pet's inventory, on the same connection as the player, the pet, and the effects. Item writes that happen outside a save still go through the queue, which keeps the batching where it helps.

What it cost

  • A save holds row locks longer. The whole save is one transaction, so its locks live until the commit. The transaction covers only one player's rows, and nothing else writes those rows in the meantime.
  • Two write paths for items. The queue still serves writes outside a save. A queued write and a save of the same item are serialized by the row lock, and the queue rechecks the flags before it writes. That rule has to stay true as the code changes.
  • Implicit context. A thread-scoped transaction is invisible at the call site. Code that hands work to another thread leaves the transaction behind. This is the price of not rewriting every call; the Javadoc says it plainly, and saves run on one thread.

How it is verified

The test that guards this is PlayerItemSavePostgresTest, and it runs against PostgreSQL 18, not a mock:

  1. Store an item with a count of 4. Change it to 9 in memory, and create a new item with a count of 3.
  2. In one transaction, write both items and the player with a new title, then throw.
  3. Make the pool open fresh connections, as after a restart, and read the database. The title is unchanged, the new item does not exist, the old item still has 4. In memory, both items know they are not stored.
  4. Save again, without the failure. Read again from fresh connections: the title, the new item with 3, and the old item with 9 are all there.

Step 3 is the one that matters. Reading through fresh connections proves what was committed, not what one connection happens to see.

The same scope later carried two more fixes of the same shape: replacing a subclass deletes the old row and inserts the new one in one transaction (#203), and a subclass whose delete rolls back stays both in the database and in memory. And on every merge, the pipeline logs a client in, creates a character, restarts the server, restores a backup into a clean stack, and checks that the character is still there.
