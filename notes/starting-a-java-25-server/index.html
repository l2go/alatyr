Starting a Java 25 server: G1, ZGC, and an AOT cache that did not help

Measured in CI on the 3.1.1 release: the server is ready in about 17 seconds on G1 and 20 on ZGC, ZGC holds almost twice the memory, and the Java 25 AOT cache changes nothing. The reason is where the time goes.

30 October 2026 · 5 min read

Java 25 arrived with two promises for a server like this one: ZGC, a collector with pauses short enough to forget about, and an ahead-of-time cache that makes the JVM start faster. Both are easy to turn on. The question was whether either one was worth it for a game server whose start is dominated by loading a world. I measured instead of guessing.

How it was measured

The pipeline has a startup job that runs only on request, because a run takes about twenty minutes and a shared runner is too noisy to gate a merge on. It builds the image and runs deploy/measure/startup.py against it.

The script starts the real stack with Docker Compose and reads a line the server prints when both ports are open: "Platform ready in N ms", with the time broken down by phase. The clock starts with the JVM, so Docker and the health check are not in the number. Ten seconds after the ports open, the script reads the resident memory of the server process.

Each configuration is measured three ways:

  • Cold: the first start, on an empty database. Migrations run and the game catalog is loaded.
  • New container: the next start in a fresh container, on the loaded database.
  • Restart: three restarts of that container; the table shows the median and the range.

The numbers below come from one run on the v3.1.1 tag: run 38302680393, commit e0f5a28, a GitHub-hosted ubuntu-24.04 runner with 4 CPUs and 15.6 GiB of memory, Docker 28.0.4. The heap is -Xms1g -Xmx3g in every configuration. The raw data is kept with this article.

Where the time goes

Of the 17 seconds on G1, the JVM spends about 0.7 before main, preparing the login module takes about a second, and the world takes the remaining 15. Starting the world means reading the game catalog, building the in-memory world, and loading the datapack: 449 Python scripts that run on Jython. That is application work, not JVM work.

This explains everything else in the table.

The AOT cache did nothing measurable. Java 25's AOT cache stores classes already loaded and linked, plus profiling data, so the next start can skip that work. It helps when class loading dominates the start. Here it does not: "before main" did not move, and the world phase is the same within noise. The restart median went from 16.9 to 16.8 seconds, inside the range of the runs. A cache file that has to be trained, stored in a volume, and kept matched to the image is not worth a tenth of a second.

ZGC costs three seconds and a gigabyte. ZGC started about three seconds slower and, ten seconds after the ports opened, held 2.3 GiB against G1's 1.3 GiB with the same -Xmx3g. ZGC is built to keep pauses short under concurrent load; while the world loads it pays for that with more concurrent work and with memory it has already committed. A Lineage II server's pause budget is generous: a G1 pause of tens of milliseconds during a fight goes unnoticed. Under a 4 GB container limit, a gigabyte of headroom is noticed.

Cold is only a second slower. Running every migration and loading the whole catalog into an empty database adds about one second over a start on a loaded one. PostgreSQL is not the bottleneck; the world is.

The flight recorder is cheap. Running Java Flight Recorder all the time, with the last 12 hours kept on disk, costs about a quarter of a second before main and about 65 MiB of resident memory in this run. That buys the ability to open a recording of the minutes before an incident without having to reproduce it.

The decision

The default is G1 without an AOT cache, with the flight recorder on. Operators can change the JVM options with L2JFREE_JAVA_OPTS, and the measurement is one click away for anyone who wants to check a different configuration.

What it cost

  • A tuning opportunity left on the table. If world loading ever becomes fast, the AOT cache may start to matter, and the measurement should be run again. The decision is recorded as conditional, not final.
  • Small samples on shared hardware. One run, three restarts per configuration, on a runner that other jobs share. Differences under half a second are noise here, and the article treats them that way. The differences that drive the decision, three seconds and a gigabyte, are an order of magnitude larger than the noise.
  • ZGC's strength is not tested here. This measures the start, not a server full of players. A load test with real traffic might favour ZGC's pauses. With the current numbers, there is no reason to pay for it in advance.

How to repeat it

Run the build workflow by hand on a release tag from v3.1.1 to v3.2.1; the startup job attaches startup.json, startup.md, and the summary table to the run. The script itself needs only Docker and Python, and its output names the configuration, the options, and every individual start, so a reader can check the medians instead of trusting them.

Update, 30 October 2026. These numbers belong to the Java server. On 29 October main replaced it with a server written in Go, and the startup job left with the JVM options it compared; it remains in the workflow of every release tag from v3.1.1 to v3.2.1. The start of the Go server has not been measured this way. Until it is, this note says nothing about it.
